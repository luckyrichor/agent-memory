# agent-memory 面试级完善方案

Oct 16, 2026 · @sh6\_apple

## 1. 目标、原则与诚实边界

**目标**：让 agent-memory 在大厂关注的那些指标上整体提升，例如 p99 延迟、扩展性、检索质量、数据新鲜度、有无记忆对比、token 消耗等。这些只是示例，不限于此，也不要只针对其中几项做优化。判断标准是三件事：每个结论有数据，每个设计有取舍，每个不足被如实说明。

**本文的使用方式**：本文是开发 Agent 的任务依据。每一项都写成可直接执行的任务：做什么、怎么测、通过标准是什么。不规定实现代码，实现方式由开发 Agent 自行设计；指标定义、数据切分和验收标准不得擅自修改。

### 五条原则

1. **先测基线，再谈提升。** 所有优化都以冻结的基线版本 B0 为起点，没有优化前的数字就没有“提升了多少”。
2. **数据口径诚实。** 没有真实生产流量，就不称“生产数据”。每个数字都标注数据等级。
3. **每个数字配四件套。** 数据集、规模、评测方法、对照基线。缺一项，该数字不进对外材料。
4. **绝对正确性不求“越高越好”。** 跨租户泄漏必须为 0，幂等必须 100%，过期 worker 覆盖新结果必须为 0，用测试和故障注入证明。
5. **一次只改一件事，收益与代价一起报告。** 变快是否牺牲召回，降低调用量是否降低质量，必须同时写明。

### 数据口径的四个等级

| 等级 | 数据来源 | 对外称呼 | 可信范围 |
| --- | --- | --- | --- |
| A | 公开基准（LongMemEval、LoCoMo、PerLTQA） | “在公开基准 X 上，与已发表方法可比” | 最高，别人可复现 |
| B | 自建并经标注的中文评测集 | “自建 N 条，双模型标注加人工仲裁，一致性 κ=…” | 高，需披露标注方法 |
| C | 合成大规模数据 | “内容为合成，性能数字为实测” | 只用于性能类指标，语义类结果不可信 |
| D | 自用日志 | “自己使用的真实日志，规模小” | 只讲真实问题，不下统计结论 |

**禁止事项：** 把 C 级数据的语义类结果说成真实效果；把小样本结果说成统计结论；报告只给均值不给分布；挑选对自己有利的子集而不披露。

### 本方案的边界

- 没有真实用户，因此不做留存、满意度、线上 A/B 等线上指标，只在材料中说明“尚无线上数据，用什么替代”。
- 公开基准以英文为主。中文结论只来自 PerLTQA、DuLeMon 与自建中文集，不把英文分数说成中文效果。
- 记忆正文会发送给第三方模型（运行时的火山 Ark，评测时的腾讯云），这是已知的数据出境点，需要在数据流向说明中如实写明（见第 9 节）。

## 2. 现状与已知缺口

**工程底座已经扎实，欠缺的是“规模下的证据”。** 以下基于 1e2730c 版本（2026-10-13）；标“核实”的项由开发 Agent 在阶段 0 确认。

### 已有的能力

- 多租户隔离：租户身份只来自 JWT；PostgreSQL 行级安全（启用并强制）；运行角色无超级用户和绕过权限。
- 数据一致性：记忆版本不可变；乐观并发；幂等键（7 天保留）；任务租约加过期写入防护。
- 混合检索：词法（含中文二元组索引）、向量（1024 维、余弦）、结构化三通道；先过滤再排序；加权倒数排名融合；响应可解释。
- 抽取与上下文：LLM 抽取器只提议内容、服务端决定范围与权限；M6 上下文构建器带预算、信任标记与防注入声明。
- 工程质量：212 个测试、ruff、严格类型检查（67 个文件）、foundation 评测 8/8。

### 缺口清单

| 缺口 | 现状 | 处理 |
| --- | --- | --- |
| 评测规模过小 | 基线 3 到 4 个用例，中文检索 6 条记忆、8 个查询，抽取 12 个事件 | 已有数字不作为证据，在大集合上重测 |
| 基线为构造而成 | “朴素向量”基线按必然失败设计 | 重新认真实现朴素基线（第 6 节） |
| 搜索每翻一页重做完整召回融合 | 候选上限 3000，offset 不超过 2900 | 压测主要瓶颈候选，对应 O1 |
| 向量索引 | 已确认无 HNSW 或 IVFFlat，向量通道为精确检索 | O2 有明确基线 |
| 证据引用为空 | 证据表在写入，上下文接口返回空数组 | O8 打通 |
| 冲突检测未做 | 上下文标记为 not\_assessed | O8 实现 |
| 上下文预算按 UTF-8 字节估算 | 偏保守，非真实 token | O6 换真实分词 |
| 敏感过滤为正则 | 保守拦截，非数据防泄漏 | 评测漏放率与误拦率 |
| 未常驻部署 | 仅有 systemd 模板与采集器示例 | 阶段 6 部署到腾讯云服务器 |
| 无租户开通与计量 | 未见相关代码 | 本方案不做 |

### 阶段 0 必须完成的修复与核实

1. InvalidScope 在应用入口没有异常处理器，可能返回 500：补上并加测试。
2. foundation\_runner 的异常捕获过窄：复核并修正。
3. 事件接口在 6a10a00 版本只接受 tool.result 一种类型：核实当前版本，若仍受限，为对话消息增加事件类型或在导入适配器中映射。
4. 租约过期判断用数据库时间还是应用机器时间：核实，应以数据库时间为准。
5. 资源滥用限制（超大请求体、超长查询、极深分页）是否完备：核实并补齐。
6. 对依赖锁文件做一次漏洞扫描。

阶段 0 只修错，不做优化；修完后的版本打标签 B0，作为全部对比的起点。

### 已确认的环境与决定

| 事项 | 结论 |
| --- | --- |
| 被测服务器 | 腾讯云，4 vCPU（AMD EPYC 7K62），内存约 8 GB，磁盘 120 GB SSD（VirtIO）。服务、数据库、worker 同机 |
| 首期规模 | 记忆条数 1 万、十万两档。100 万及以上暂缓，等有更大内存的机器再做 |
| 压测机 | 首期用项目负责人的 Mac 笔记本作发压端，口径见第 8 节 |
| 向量模型（运行时） | 火山 Ark 的 doubao-embedding-vision-251215，请求设 dimensions=1024。限流 RPM 15,000、TPM 1,200,000（上限，非余额） |
| 对话与抽取模型（运行时） | 火山 Ark 的 doubao-seed-2-1-pro-260915，RPM 30,000、TPM 5,000,000 |
| 评测用模型 | 腾讯云 TokenHub 的 API Key 下的非豆包系列模型，用于标注与裁判，选型见第 7 节；腾讯云向量模型参与对比实验（O10） |
| 向量索引 | 当前无近似索引，精确检索即为基线 |
| 人工标注力量 | 只有项目负责人一人，采用“两个模型标注、负责人仲裁、抽检 10%” |
| 开发与交接 | 开发 Agent 在本地 Git 仓库工作并同步到 GitHub（luckyrichor/agent-memory）；每个阶段结束时交付代码提交、报告、运行命令和环境指纹 |
| 不做的事 | OpenAI 官方口径对照；100 万以上规模；租户开通与计量；线上 A/B |
| 模型分工 | 采用第 7 节的分工；预检不达标再按备选替换 |
| 延迟预算 | 假设单轮 3 秒、记忆检索占 10%，得出检索 p99 目标约 300 毫秒；这是假设，基线测完后复核 |
| 向量模型切换规则 | O10 中腾讯云向量模型质量持平或更优则切换线上模型，规则见 O10 决策规则 |
| 限流与配额 | 不预先查询 RPM/TPM；遇到 429 按退避重试；预检只确认模型能调用 |
| 用量记录 | 不做费用考量，只记录模型调用次数与 token 用量 |
| 仓库公开规则 | 仓库与对外材料公开。数据集本体不进仓库，只放清单、哈希和下载脚本；LoCoMo、PerLTQA、RiSAWOZ（CC BY-NC 4.0）按协议署名并附协议链接；不提交密钥与真实记忆数据 |

**数据出境原则**：记忆正文发送给第三方模型后，对方是否留存、是否用于训练，只能引用其服务条款，无法验证。所以评测阶段发给腾讯云模型的只有公开数据和合成数据，不发送真实用户记忆。

**阶段 1 需要核实并记录的信息**：Ark 向量模型的批量输入方式与单次输入上限；各评测模型的可调用状态（每个模型发一次最小请求确认）。不需要预先查询 RPM/TPM，运行中遇到限流（429）按退避重试即可。

## 3. 指标体系总表

**共八层、约 50 个指标，每个指标有编号、口径、数据要求。** 编号在代码、报告与对外材料中统一引用。“类型”列：标准 = 领域公认定义；基准 = 由公开基准规定口径；自定义 = 记忆系统特有，没有公认口径，需在报告中写清定义。

通用约定：比例类指标都给出分子分母与样本量，并给出 95% 置信区间（自助重采样法，1000 次）；延迟类指标报告 p50/p95/p99 与样本量，不只报均值。

## 4. 大厂重点优化指标

**六个指标是门面，不是全部。** p99 延迟、扩展性、检索质量、数据新鲜度、token 消耗、有无记忆对比，对应评审中最常被问的“优化了什么”。追问还会延伸到稳定性、公平性、可回滚和最差的那一类查询，所以重点扩为三档。

说明：下表是互联网在线服务和检索系统的通用做法加对 agent 方向的判断，不代表任何一家公司的内部口径，对外材料不得声称知道某家的内部指标。

### 第一档：必须有优化故事（“优化前后”对比图）

| 指标 | 对应编号 | 大厂为什么关心 | 优化手段方向 |
| --- | --- | --- | --- |
| 搜索 p99 延迟 | PF1 | 看长尾不看平均，长尾直接导致上游超时 | 分阶段归因；只取页内正文；查询向量缓存；结果集缓存；近似索引 |
| 扩展性曲线 | PF5、PF4 | 要证明能扩到多大、拐点在哪 | 索引调优；候选上限；分区；连接池 |
| 检索质量 | RT1 到 RT5 | 效果是业务价值根本，且必须分题型看 | 消融定位、失败案例归类、定向改进最差题型 |
| 单位用量 | SC5、SC6、E3 | 模型调用是最大的资源消耗，大厂对 token 消耗和调用次数很敏感 | 批量向量化；查询向量缓存；只对变更重算；上下文预算压缩 |
| 数据新鲜度 | PF7、PF8 | 写入后搜不到会直接让智能体“忘事” | 轮询间隔、批大小、并发度、触发式唤醒 |
| 有无记忆对比 | E2、E6 | 证明记忆真的带来业务增益 | 四组对比 + 距上限差距分析 |

### 第二档：体现工程成熟度（必须有数据，可以没有“优化前后”）

| 指标 | 对应编号 | 说明 |
| --- | --- | --- |
| 长尾稳定性 | PF1 衍生 | p99 与 p50 的比值，越接近 1 越稳 |
| 缓存冷热差异 | PF1、SC7 | 冷启动与稳态的延迟差，重启后预热耗时 |
| 单核吞吐 | PF4、PF9 | 每核每秒处理请求数，用于容量规划 |
| 单实例承载上限 | PF5 | 延迟达标前提下，单库能承载的记忆条数 |
| 多租户公平性 | PF10 | “吵闹邻居”影响倍数 |
| 可用性与故障恢复 | RL5、RL7 | 故障注入下的恢复时间和错误率 |
| 变更回滚耗时 | OP1（新增） | 换向量模型、改融合权重、迁移结构后，从发现问题到回滚完成的耗时 |
| 换模型期间可用性 | OP2（新增） | 重建向量期间检索质量与延迟的变化，重建总耗时与总 token 数 |
| 备份恢复 | RL6 | 恢复耗时与完整性 |

OP1、OP2 是第 3 节未列的新指标，由开发 Agent 在评测框架里补上：OP1 = 从触发回滚命令到指标恢复到基线的秒数；OP2 = 重建期间每分钟采样的 RT1 与 PF1，及重建完成总时长。

### 第三档：记忆系统特有的深度指标（区分度最高）

LC3 冲突处理准确率、LC4 过期记忆泄漏率、LC1 和 LC2 去重与误合并、EX1 到 EX3 抽取质量、RT6 拒答正确率、CX3 关键信息保留率、CX6 注入防御。这些没有公认口径，每个指标的定义依据必须写进报告。

### 绝对正确性指标（不优化，只验证）

SC1 跨租户泄漏 = 0、RT10 过滤正确性 = 0、RL1 幂等 = 100%、RL2 丢失更新 = 0、RL3 过期覆盖 = 0、SC3 权限绕过 = 0、SC4 日志泄漏 = 0、LC5 非法转换拒绝 = 100%、LC7 删除残留 = 0。任何一项不达标，该阶段不算完成。

### 目标值怎么定

1. **不提前拍数字。** 所有目标值在基线测量完成后再定，本文不给绝对目标。
2. **用“预算分摊”定延迟目标。** 先假定智能体单轮可接受延迟（示例 3 秒），再规定记忆检索最多占其中 10%，得到“检索 p99 ≤ 约 300 毫秒”。两个假设值在基线测完后复核（见第 2 节已确认的决定），对外必须说明是假设。
3. **质量用“显著性”定。** 提升必须超出置信区间重叠的范围才算数；提升不大时，说清“在哪类题型、为什么”。
4. **资源用量用“单位”定。** 每千次写入、每千次检索、每个答对题的调用次数与 token 数，不用总量。
5. **每个优化项写代价。** 变快是否牺牲召回、省钱是否降了质量，两者同时汇报。

**真实中文金标准的补足路径（负责人已确认）**

- DuLeMon 自带标签的人工一致率实测仅 24.84%（39/157，抽样不是随机的，上界 48.7% 仍低于 95%），不能直接当金标准，只采用人工确认过的部分（当前应记 22 条）。
- 补量：对双模型共同保留池（711 条）重新固定种子、独立随机盲抽 72 条由负责人人工核对，错误不超过 3 条则通过，不得复用按旧标签挑选的样本。通过后，再从未用过且有所需字段的 DuLeMon 对话里按固定种子增量取样，沿用冻结的两个标注模型，缺额用实际新增且通过抽检的记忆点补足，不能用预期产出宣称达标。抽检不通过时仍只保留人工确认项。
- 拟作负样本的完整会话另行确认，以保证会话数量与负样本比例。

**时间推理、知识更新、多会话三类查询（负责人已确认）**

- 这三类原先全部来自程序构造的时间线（结构与顺序可直接预测标签，只作流程验证）。改用独立困难集 synthetic-hard-v1 替换来源：打乱顺序与 ID、正负平衡、加入归属与临时性难例，并做打乱、遮蔽、反事实对照。新版查询与旧版不可同集比较。
- 仍是程序构造，只作“流程验证”：阶段 2 必须把这三类题型单列，不得把高分解读成真实中文的时间推理、更新或跨会话能力，也不得用混合总分宣称质量提升。

**可选补充评测：PAL-Set（负责人已确认，阶段 2 以后再考虑）**

- Mem-PAL 论文（AAAI 2026）的 PAL-Set 是公开的中文长期个性化交互数据：100 个合成用户、约 2900 个会话、826 个带隐含需求的任务话题，由模型生成、经人工抽查；许可声明为 CC BY-NC 4.0、仅供研究，不得放入本项目仓库再分发。
- 它没有逐条“应记/不应记”人工标签，也没有证据对应到具体轮次的标注，因此不能当抽取金标准，也不能用来算检索召回，不计入真实中文金标准规模。
- 可选用途：阶段 2 之后作为中文端到端个性化评测（个性化命中率、有无记忆对比）的补充，需模拟用户与裁判校准，必须单列报告并标明“作者模型生成”。阶段 1 不做。

**两层记忆设计：长期与短期（负责人已确认）**

- 阶段 1 的抽取目标是长期记忆：只记跨会话长期有效的偏好、身份、事实和长期计划。临时状态（如“我感冒了”“明天妈妈来看我”“现在正在拍电视剧”）判为不记。这是设计选择而不是对错题，评测与金标准按此执行，不中途更改。
- 边界的经验法则（不是冻结规则）：问“一个月后这件事还成立、还有用吗”，成立则记。标注与模型提示词里都要明确判断时效性：模型对每条 keep 额外给出“长期”或“临时”，临时的不得 keep。
- 留痕：人工核对时，凡因“临时”判 discard 的，理由里写“临时”二字，以便以后直接复用为短期记忆标注集。
- 短期记忆（带有效期，如“这周感冒”，到期自动失效）作为阶段 2 之后的可选增强项，单独设计、单独评测：抽取时增加“有效期”判断，标注新增“短期”类别，指标新增“到期后是否自动失效”，并与「过期记忆泄漏率」配合。阶段 1 不做。
- 健康类等敏感信息即使是短期也要按敏感信息规则处理，不因为是临时的就放宽。

“规模目标”是设计下限，用于保证比例类指标的置信区间不会宽到没有意义。实际规模以标注能力为准，但不得低于此值后仍报告统计结论。

### 标注与划分规程

1. **双模型标注加人工仲裁。** 先由两个不同厂商的大模型分别标注（模型见第 7 节），项目负责人只仲裁两者不一致的条目；用 Cohen κ 报告“模型与模型”的一致性，再从最终标签里随机抽 10% 由负责人复核，报告“模型与人”的一致率。目标 κ ≥ 0.7，低于此值说明标注指南不清晰，先修指南再继续。κ 门槛适用于 DuLeMon 与合成数据，ECD 不要求双模型 κ（见下文客服场景）。数据集自带的原生标注（DuLeMon、PerLTQA）如果经负责人抽检与人工一致率低于 95%，不得直接当金标准，只采用人工确认过的子集。标注模型额度不足时可自动切换，切换后整批重标并说明原因。
2. **写标注指南。** 什么算“应该记”、什么算“正确”、什么算“相关”，每条规则配正反例，指南随数据集一起维护。
3. **开发集与测试集分开。** 30% 开发、70% 测试，按对话而不是按条目切分。调参和看失败案例只用开发集；测试集只在里程碑报告时跑，测试集哈希写入报告。
4. **公开基准的污染风险。** 公开基准可能已出现在某些模型的训练数据里。报告中写“未确认是否存在训练数据污染”，并用自建中文集作为不受此影响的对照。
5. **人工力量的局限。** 只有项目负责人一人，没有第二位人工标注者。仲裁和抽检时不显示系统输出，避免被系统结果影响；报告中必须写明“单人仲裁”。

### 自建中文评测集的场景方案

“自建”指在公开数据上补充所需标注，或按“事实时间线”合成多会话对话，不凭空编造对话。分三层：

1. **通用中文层（有现成标准答案）**：DuLeMon 加 PerLTQA 的 zh 版。DuLeMon 评抽取与检索，PerLTQA 评问答。
2. 客服场景（主场景）：真实对话用淘宝客服对话语料 ECD，用途有两个。一，负样本集，测“不该记的内容有没有被记下来”（抽取层的误抽指标）。二，小规模真实客服金标准：从 ECD 抽 100 到 150 段对话，由项目负责人直接人工标注“哪些应记”，不用双模型 κ 门槛。原因：ECD 是客服事务对话，几乎没有值得长期记的用户信息，阶段 1 实测两个模型共同保留 0 条、κ 仅 0.154，用双模型标注生成金标准不可行。ECD 是单次会话的对话数据，没有“同一用户的多次来访”，多会话部分用合成补齐。合成方法：先为每个虚构用户写一张“事实时间线”（地址变更、退款从申请到到账、偏好、投诉），再让大模型按时间线生成 3 到 6 个会话；题目和标准答案直接来自时间线，只需项目负责人抽检约 10%。天然覆盖知识更新、时间推理和拒答。ECD 拿不到或不完整时，客服场景只用合成数据，不阻塞其他工作。

所有合成数据在数据清单里单独标记“合成”，订单号、姓名、手机号都用虚构的。规模目标以第 5 节“专项集规格”为准。

### 合成压测数据的生成原则

合成数据的目的是让性能数字贴近真实，细节上要注意四点：

1. **分布要像真实。** 租户规模不均（少数大租户占大部分）、记忆长度有分布、主题有集中度，不等长等量。
2. **向量不能用随机向量。** 随机向量的近邻结构与真实文本向量完全不同，近似索引的召回率和延迟会失真。必须用真实文本的真实向量。
3. **用量。** 首期规模不超过 10 万条，全部用真实文本向量化（约 1000 万 token），不使用扰动派生向量。将来扩到 100 万以上时才引入“真实向量加小扰动”，并在报告中标注比例。
4. **报告必须标注“内容为合成”。** 性能数字是实测，语义效果不靠这部分数据。

### 基准导入方式

每个基准都用两种模式跑，目的是分离抓取质量与检索质量。

| 模式 | 做法 | 作用 |
| --- | --- | --- |
| 直写模式 | 把基准对话的轮次或会话直接写成记忆，跳过抽取 | 只测检索、上下文、端到端，排除抽取误差的影响 |
| 全链路模式 | 对话作为事件写入，经抽取器生成记忆，再检索与回答 | 测真实系统的端到端效果，并解释两模式差距来自抽取 |

两个关键技术点：

- **证据映射。** 基准的检索召回按“证据会话或轮次”标注。导入时必须记录“记忆编号到来源会话或轮次”的映射（可利用证据表），否则算不出召回。这也是第 10 节“打通证据引用”的前置任务。
- **事件接口限制。** 以阶段 0 的核实结论为准；若仍只接受 tool.result，需为对话消息增加事件类型，或在导入适配器中映射。

## 6. 评测框架设计

**所有实验用一条命令跑完，结果自动落成带版本的报告，任何人拿到同一个提交和同一份数据都能复现同样的数字。** 没有这个框架，“优化前后”就是一句空话。

### 框架的六个要求

1. **单一入口。** 一个评测命令，参数是：数据集、模式（直写 或 全链路）、系统配置、指标集合。不允许手工拼接多个脚本。
2. **结果全量留痕。** 每次运行保存：代码提交号、配置、数据集版本与哈希、随机种子、模型名与版本、运行环境、每题的原始结果（不只是汇总）。
3. **可复现。** 外部模型输出有随机性，所以温度设 0，记录每次调用的输入输出，同一批数据允许“重放”缓存结果，避免重复花钱。关键结论要跑 3 次以上并报告波动范围。
4. **基线冻结。** 基线版本打标签、结果存档、不允许覆盖。后续所有“提升”都在报告首行写明对比的基线标签。
5. **自动对比。** 两次运行的结果自动生成对比表，包含差异、置信区间、是否显著，以及“变好的题”和“变差的题”的清单，防止只报喜。
6. **退化护栏。** 把绝对正确性指标（第 4 节）和一组核心质量指标放进持续集成。任何提交导致这些指标退化，直接失败。

### 结果报告的固定结构

每一份报告都有这几个栏：

| 栏 | 内容 |
| --- | --- |
| 头部 | 提交号、日期、基线标签、环境、随机种子、模型版本 |
| 数据 | 数据集名、版本、规模、哈希、数据口径等级（第 1 节 A 到 D） |
| 指标 | 指标编号、值、样本量、置信区间 |
| 对比 | 与基线的差异、显著性、变好与变差的题目清单 |
| 分题型 | 每个题型的指标，最差题型高亮 |
| 失败案例 | 至少 20 个失败案例，按原因归类 |
| 资源用量 | 模型调用次数、token 数、数据出境量（SC8） |
| 局限 | 该次评测的已知局限，写清楚影响 |

### 基线定义

“基线”指第一次完整测量时的系统，也就是 1e2730c 修复第 2 节中“先修”的小问题后的版本（只修错，不优化）。标签命名为 B0。对比用的外部基线还有三个：

- **无记忆**：智能体不带任何历史。
- **全文塞入**：把完整历史直接放进上下文，受模型上下文限制，超长的按截断处理。
- **朴素向量检索**：只用向量一个通道，不做过滤、不做词法、不做融合。

朴素向量检索必须认真实现，不能特意写弱。现在项目里的“朴素向量”基线是为了让它失败而构造的，对外说明时经不起质疑。

### 代码与目录约定

- 评测代码放在项目现有的 evals 目录下，与业务代码隔离，评测代码只通过公开 API 与 SDK 访问系统，除非测内部指标。
- 结果与报告目录按“日期 + 提交号 + 数据集”归档，原始数据和汇总分开存。
- 大文件（数据集、原始结果）不进代码仓库，只保存清单和哈希，并写明如何重新获取。
- 每个指标的计算代码配单元测试，用一组手算可验证的小样例确认公式实现正确。指标算错，比系统有问题更致命。

## 7. 裁判模型方案

**裁判与标注模型使用腾讯云 TokenHub 上的非豆包模型，并用人工校准证明裁判可信，不把结果直接与论文中的 GPT-4o 分数比较。** 评测里只有少数指标需要裁判（E1 问答准确率、E4 幻觉率、CX5 冗余率），检索、性能、正确性指标都不需要。

**裁判选择与切换规则**

- 选择：由开发 Agent 在已有 API Key 的腾讯云 TokenHub 与火山 Ark 的可用模型里，筛出同时满足下列条件的候选：账号当前能调用；能关闭思考且温度 0 实际生效（过下面的 5 次一致预检）；与答题模型的厂商不同，且与这张对比表所用数据的标注厂商不同（不同对比表可以用不同裁判，各自遵守本条）。不按剩余额度排序，也不要求提供控制台额度截图：按“预检通过且实际调用成功”选定主裁判，其后至少一个同样通过的为备选（账号可用模型有限；备选用完且无可用模型时暂停并报告，不放宽预检门槛）。
- 额度兜底：不查余额。开跑前用“调用量估算”算出所需判分调用次数和 token 并记录；运行中额度用完，由下面的“额度不足时的统一切换规则”兜底。
- 切换：主裁判额度用完或持续调用失败时，自动改用备选。但同一张对比表里只能出现一个裁判的判分，否则分数不可比；中途切换时，该对比表整体用新裁判重判。每条判分结果记录裁判名称与版本。
- 校准：每个会用到的裁判都要做人工校准（见下文达标线），未校准的备选不得用于正式结果。
- 报告：写明实际使用的裁判、切换时间点和原因。

**额度不足时的统一切换规则（适用于所有任务）**

- 总则：任何任务在调用大模型时遇到额度不足（如 HTTP 402、免费包耗尽），立刻换用同角色已预检通过的备选继续，不停下等人。同一张结果表只能出自同一个模型，这一条优先于“立刻继续”。
- 触发条件：只在额度类错误时切换。超时、限流、普通失败先做有限次重试，仍失败才切换。
- 备选要求：必须是已通过预检的模型，且各角色之间“不同厂商”的约束继续有效。腾讯云与火山 Ark 是渠道，不是厂商，同一厂商的模型换渠道不算独立。
- 裁判：整张对比表用新裁判从头重判，旧的部分分数只留失败台账，整表完成后才发布。
- 答题模型：可以切换，但同一组对比里的所有结果要用新模型整组重跑，否则基线与后续版本不可比。
- 标注模型：额度不足时可自动切换（火山不足优先腾讯），负责人已授权，不再逐次确认。切换后受影响的一侧整批重标，不混用新旧标签，不放宽引用校验与盲审标准，并报告对裁判池厂商排除的影响。
- 运行时抽取模型与向量化模型：不自动切换。前者是被测对象，中途更换会污染评测；后者更换会改变向量空间，索引必须全部重建。额度不足时暂停并报告。
- 造数据、探测等不进入评测结果的任务：可以直接切换。
- 记录：每次切换都写入日志，包含时间、原因、切出与切入的模型、受影响的结果表；每条结果记录所用模型名称与版本。

### 主流程设计

| 角色 | 模型（调用 ID） | 平台 | 理由与参数 |
| --- | --- | --- | --- |
| 向量化（运行时） | doubao-embedding-vision-251215，dimensions=1024 | 火山 Ark | 项目既有依赖；与腾讯云向量模型的对比见 O10 |
| 抽取与对话（运行时） | doubao-seed-2-1-pro-260915 | 火山 Ark | 项目既有依赖，限流已知 |
| 答题模型（端到端评测） | doubao-seed-2-1-pro-260915 | 火山 Ark | 代表项目实际使用的对话模型；与裁判不同厂商，避免自偏；可选 hy3 做一次对照，检验结论是否随答题模型变化 |
| 标注模型 A | deepseek-v4-pro，关闭思考（预检观测到生效） | 腾讯云 TokenHub | 官方支持温度 0 |
| 标注模型 B | mimo-v2.6-flash（小米），关闭思考（预检观测到生效） | 腾讯云 TokenHub | 官方支持温度 0 |
| 裁判模型 | 按“预检通过且实际调用成功”选定，规则见下方“裁判选择与切换规则”。glm-5.2 曾遇 402 额度错误，glm-5.3 系列不支持关闭思考 | 腾讯云 TokenHub | 必须与标注 A、B 和答题模型都不同厂商；判分输入短 |
| 裁判备选 | 至少再选两个备选，选法同上；hy3（reasoning\_effort=none）是候选之一 | 腾讯云 TokenHub | 额度用完、调用失败或校准不达标时的替补 |

**选型依据与限制**（来自 2026-10-17 的腾讯云 TokenHub 模型清单）：

- 答题、标注 A、标注 B、裁判四个角色必须分属不同厂商（当前：字节、DeepSeek、小米，裁判另选）。答题模型是端到端评测的隐含变量，报告必须写明名称与版本，所有对比实验中保持不变。
- 清单里温度 0 “请求被接受”不等于采样参数真正生效，所以必须做下面的一致性预检。Kimi 系列采样值固定、不能设 0，不作为标注或裁判；Step 的思考开关未核实，不选；MiMo 的 mimo-v2.6-flash 已在预检中观测到关闭思考生效，用作标注 B。
- 清单没有账号的 RPM/TPM，也不代表模型已开通：预检时每个模型发一次最小请求确认可调用；运行中遇到限流（429）按退避重试，不需要预先查询配额。
- 数据集标签在评测开始前建好，不依赖项目本身；裁判则在每次评测运行时现场调用，所以评测环境必须能调用腾讯云接口，不能事后手工判分。

**模型预检（阶段 1，通过后才能用）**：

1. 每个模型发一次最小请求，确认已开通且调用 ID 正确。
2. 温度 0 与思考开关：同一条输入连跑 5 次，判分结果必须一致；不一致的模型不得作为裁判，改用备选。
3. 结构化输出：100 条样本上格式合法率 ≥ 99%。
4. 记录实测延迟与限流表现；先用小子集实测调用次数和 token 用量，再决定全量还是抽样。
5. 记录调用 ID、调用日期、参数与提示词版本。

### 和官方 GPT-4o 口径的差异

LongMemEval 的问答判分出自 GPT-4o，换成非 GPT-4o 的裁判模型后，**绝对分数与论文中已发表的分数不再严格可比**。处理办法：

1. 沿用官方评测脚本里的判分提示词结构，按题型分别使用（知识更新、时间推理、拒答等提示词不同），只替换模型。
2. 报告里一律标注裁判模型名称与版本（如“glm-5.2 判分”），不写“和已发表方法一致口径”。
3. 用校准子集证明“裁判与人工判分的一致性”，这才是可信依据，而不是“和 GPT-4o 一样”。
4. 与已发表方法的横向对比只在检索层面做（不依赖裁判）；问答层面的对比只用自己跑的四组（无记忆、全文塞入、朴素向量、本系统）。

### 人工校准规程

1. **抽样。** 从所有需要裁判的结果里分层抽样 300 条，按题型、系统分组、裁判结果（正确与错误）分层，保证错误样本不被淡没。
2. **人工判定。** 由项目负责人独立判断“答案是否正确”，不显示裁判结果；同一批样本再让标注模型 B 判分作交叉参照。
3. **计算一致性。** 裁判与人工的 Cohen κ、准确率、混淆矩阵，重点看“裁判判对但人工判错”的比例，这会高估系统效果。
4. **达标线。** κ ≥ 0.7 或与人工准确率 ≥ 90% 才采用。低于此值，修订提示词后重新校准，最多三轮；仍不达标，该指标改用纯人工抽检。
5. **自一致性。** 同一批 100 条重复判分 3 次，报告结果变化的比例。
6. **报告修正。** 把校准结果写进每份报告，必要时给出“按人工校准修正后的指标区间”。

### 裁判可靠性的其他措施

- 提示词版本化并冻结，每次报告记录提示词哈希，不允许在不重新校准的情况下改动。
- 要求裁判输出简短理由与结论，理由留档，便于失败案例分析。
- 裁判只看“问题、标准答案、系统回答”，不让它看到是哪一组的回答，避免对某一组偏向。
- 调用失败、格式不合法的结果记为“无效”并统计比例，不得默认当成错误或正确。

### 调用量估算

总调用次数 = 题数 × （答题 1 次 + 判分 1 次）× 实验组数 × 重复次数。例如 500 题 × 2 次 × 4 组 × 3 次 = 12000 次调用。答题输入带上下文，是 token 消耗大头，“全文塞入”组尤其大（S 版约 11.5 万 token 一题），所以先用小子集预估调用次数和 token 总量，再决定全量还是抽样。判分输入短，每次约 1000 token、输出约 100 token。这是估算，以预检实测为准。

## 8. 性能与容量压测方案

**压测的目标是回答三个问题：系统在多大规模下还能达标？拐点在哪、瓶颈是什么？改了之后拐点移动了多少？** 对应指标 PF1 到 PF10。这部分的数字都是实测，可以诚实地以“合成数据上的实测”表述。

### 环境要求

1. **压测机与被测服务分开部署。** 压测客户端和服务、数据库不能在同一台机器，否则互相抢资源，数字失真。
2. **记录环境指纹。** 机器型号、CPU、内存、磁盘类型、网络、PostgreSQL 与 pgvector 版本、关键数据库参数（内存、连接数、维护内存），写进每份报告头。
3. **冻结外部依赖。** 压测中不调用真实模型接口（用预先算好的向量和夹具提供者），否则测的是网络和供应商。模型调用的延迟单独测、单独报告。
4. **预热与稳态。** 每个测量点先预热 1 分钟，再采样不少于 5 分钟，重复 3 次，报告中位数和波动范围。
5. **数据库维护状态。** 大量导入后先手动执行统计信息更新，等索引构建完成和后台清理稳定后再测，并记录这些步骤。

### 负载模型

| 模型 | 说明 | 用途 |
| --- | --- | --- |
| 开环（固定到达率） | 按固定每秒请求数发送，不等上一个请求完成 | **主用**。能真实反映服务变慢时的排队，避免低估 p99 |
| 闭环（固定并发数） | 每个连接等上一个请求完成再发下一个 | 只用于找最大吞吐，不用于报告延迟 |

原因是一个常见陷阱：用闭环模型测延迟，服务一卡，压测客户端也跟着停止发送，导致慢请求被“少统计”，长尾延迟被严重低估。因此报告延迟必须采用开环。

读写比例分三档：纯搜索、搜索 90% 加写入 10%、搜索 70% 加写入 30%。再加一组“上下文接口”的压测。查询文本从中文语料中按真实长度分布抽取，不要用固定的几句话。

### 规模梯度

记忆条数为 1 万、10 万（理由见下段）。租户数 10、100、1000，租户规模按偏斜分布生成。每个规模点都重新建索引，记录建索引耗时与体积。

**首期只做 1 万和 10 万。** 粗算：1024 维向量每条约 4 KB，10 万条约 0.4 GB，加近似索引后约 1 GB，8 GB 内存的机器放得下；100 万条加索引约 8 到 9 GB，放不进内存，磁盘读会让数字失真，所以暂缓。10 万级压测时服务、数据库、worker 同机，要限制数据库内存参数并记录可用内存，导入和压测不要同时进行。

**用 Mac 当压测机：首期可以，但要按下面的口径做：**

1. 延迟报两种：服务端处理延迟（由服务自己的指标采集，不含网络）和客户端观测延迟（含网络）。p99 以服务端为准，客户端的值附上空接口往返时间作为基线，因为家用网络的抖动会污染长尾。
2. 笔记本接电源，关闭睡眠和省电，压测期间不跑其他重负载；用有线或稳定的网络。
3. 每个测点重复 3 次；同一配置三次的 p99 差异明显时，先排查网络再解读结果。
4. 发压工具必须支持“固定到达率”（open-loop），常见开源工具如 k6、wrk2 都有这类模式，具体选哪个由开发 Agent 定，并在报告里写明。
5. 10 万级的请求速率不高，Mac 的性能足够；到 100 万级需要更大内存的被测机时，再换用更大内存的机器，用完释放。

**向量化耗时估算：** 10 万条记忆，假设每条约 100 个 token，总量约 1000 万 token。按 Ark 的 TPM 1,200,000 算，理论下限约 8 到 9 分钟；按 RPM 15,000、每条一次请求算，下限约 7 分钟。加上重试和并发控制，预留 30 到 60 分钟（估计，不是实测）。向量模型的批量输入方式和单次输入上限，由开发 Agent 查文档确认。

### 实验清单

| 编号 | 目的 | 自变量 | 产出 |
| --- | --- | --- | --- |
| P1 | 延迟随规模变化 | 记忆条数 | PF1 到 PF3 的 p50/p95/p99 曲线，分阶段拆解 |
| P2 | 找到吞吐拐点 | 到达率逐步上升 | 吞吐与 p99 的关系图，拐点 QPS |

| P4 | 过滤与近似索引的交互 | 租户、工作区过滤条件的选择性 | 过滤后返回条数与召回率的下降 |

P4 是一个容易被忽略的关键点：项目采用“先过滤再排序”，而近似向量索引通常先找近邻再过滤，过滤条件严格时可能只返回很少甚至不足的结果。这是多租户加向量索引时的真实风险。较新的 pgvector 版本提供了缓解办法，具体支持哪些由开发 Agent 对照所用版本的文档确认。

### 测量方法

- **分阶段归因。** 用现有链路追踪在检索每个阶段打点：查询向量化、词法召回、向量召回、结构化召回、融合、取正文、序列化。优化之前先知道时间花在哪，不凭感觉改。项目的可观测性已有字段白名单，给注指标要在白名单内，不记录记忆正文。
- **数据库侧分析。** 用数据库自带的慢查询统计和执行计划分析，确认每个通道的查询是否走了预期的索引。
- **资源采样。** 压测期间每秒采样 CPU、内存、磁盘 IO、数据库连接数，与延迟曲线对齐。
- **每个测量点记录错误率。** 延迟不达标或错误率超过 1% 的点，不计入“达标吞吐”。

### 常见陷阱

1. 客户端与服务同机。
2. 用闭环模型报告延迟。
3. 用随机向量测近似索引。
4. 所有查询都命中同一批缓存，没有按真实查询分布。
5. 只报平均值。
6. 压测期间模型接口失败或限流，却把这部分延迟计入系统延迟。
7. 建索引或后台清理未完成就开始测量。

## 9. 可靠性、故障注入与安全评测

**这一节的指标大部分是“绝对正确”类，评价方式是通过或不通过，不是越高越好。** 两部分：主动制造故障看系统行为，以及以攻击者视角验证安全边界。

### 故障注入清单

| 编号 | 故障 | 注入方式 | 期望行为 | 验证指标 |
| --- | --- | --- | --- | --- |
| F1 | 数据库重启 | 写入压力下重启数据库 | 已确认写入不丢失，客户端收到可重试错误，恢复后自动继续 | RL5、RL7、已确认写入核对 |
| F2 | 数据库连接耗尽 | 人为占满连接 | 快速失败并返回明确错误，不拖垮其他接口 | RL7、PF1 |

每一项列“威胁、现有防御、验证方法、通过标准”。现有防御指项目文档已声明的设计，验证的目的是确认它“真的有效”。

### 备份恢复演练

备份没有经过恢复演练就不算备份。按以下步骤，结果记入 RL6：

1. 在有一定规模（至少 10 万条（首期规模上限））的库上做一次全量备份，记录耗时与体积。
2. 在另一台机器上恢复，记录恢复耗时。
3. 校验：各表行数、校验和、随机抽样 1000 条比对、用标准查询集跑一次检索确认 RT1 与恢复前一致。
4. 验证行级安全、角色、权限在恢复后的库上仍然有效（这是很容易被遗漏的一步）。
5. 演练结果和踩到的坑写进运维手册。

### 删除与合规说明（评测之外的文档任务）

为作品展示和对外产品准备两份说明文档，内容要如实：

- **数据流向说明：** 哪些数据发给了哪个第三方模型、用途、是否留存（如果供应商条款写了就引用，没写就写“无法验证”）。
- **删除说明：** 逻辑删除、物理清除各自触发条件、覆盖范围（包括向量、事件、备份）、预期时限。

### O10：向量模型对比实验（Ark 对腾讯云，1024 维）

**目标**：在不改变表结构（向量列固定 1024 维）的前提下，比较两个向量模型的检索质量、延迟、用量与稳定性，给出是否切换的结论。O10 须在 B0 之后、O2 之前完成，避免换模型后重做索引实验。

| --- | --- | --- | --- |
| Ark（现用） | doubao-embedding-vision-251215，请求设 dimensions=1024 | 1024 | 多模态向量模型，当前只用于文本 |
| 腾讯云（主要对比对象） | kinfra-text-embedding-0.6b | 原生 1024 | 纯文本向量模型 |
| 腾讯云（可选） | kinfra-text-embedding-4b | 原生 2560 | 仅当官方文档确认支持降到 1024 维才进入同表对比；否则只在隔离的小规模实验里按原生维度比较，不改线上表结构 |

腾讯云的 kinfra-vl-embedding-2b（2048 维）与 8b（4096 维）是多模态模型，项目只存文本，不纳入。

**公平性规则**

1. 同一批文本、同一套切分、同一批查询与标准答案。
2. 按各家官方文档，对查询与文档分别使用其要求的输入格式或指令前缀，并记录所用格式。
3. 距离函数与向量归一化处理一致（余弦），检索通道与融合参数一律不变；向量通道两边都用精确检索，避免索引差异混入。
4. 每个模型使用独立的向量集合（用向量表里的模型标记区分），同一次查询只匹配同模型向量。
5. 每个实验重复 3 次，报告波动范围。

**对比指标**

| 维度 | 指标 | 数据 |
| --- | --- | --- |
| 质量 | RT1 到 RT5，英文与中文分开报告 | LongMemEval（S、oracle）、PerLTQA zh、DuLeMon、自建中文检索集 |
| 延迟 | 查询向量化延迟 p50/p95/p99，在腾讯云服务器上测，含到各家接口的网络 | 真实长度分布的查询 |
| 吞吐与稳定性 | 批量向量化吞吐、限流与失败比例、重试次数 | 10 万条记忆全量向量化 |
| 用量 | SC5、SC6（调用次数与 token 数） | 调用日志 |
| 切换代价 | 全量重建耗时（OP2）与回滚耗时（OP1） | 10 万条规模 |

**决策规则**（已确定）：质量差异落在置信区间重叠范围内视为持平，持平时按延迟、稳定性、token 与调用用量择优；质量差异显著时质量优先，同时报告用量变化。不把英文基准的差异外推到中文。切换只能通过全量重建，由 F10 的不停服重建流程执行。结果无论谁胜出，都作为一个优化故事交付。

### O8：四项记忆深度能力的设计简述

以下是设计思路，细节由开发 Agent 在开发集上迭代。每一项都要先写“目标行为”，再写指标，最后才实现。

**1. 冲突处理（对应 LC3、LC4）**

- 目标行为：用户先说“我住北京”、后说“我搬到上海了”，检索和上下文里只应出现最新的，且旧版本可追溯。
- 思路：写入新记忆时，先找“同一主体、同一属性”的已有记忆，判断是“补充”“重复”还是“矛盾”。明确矛盾且新说法来自用户直接陈述，就用项目已有的“取代”状态和继任者字段；不确定时两条都保留并标记待复核，不自作主张。
- 关键点：“同一属性”怎么判断是难点，候选方法是先用检索找相似记忆，再用模型判断关系，模型判断的准确率单独评测。

**2. 去重与合并（LC1、LC2）**

- 目标行为：“用户喜欢深色主题”和“用户偏好暗色界面”不应变成两条独立记忆。
- 思路：分两级。内容哈希相同直接判重；向量相似度超过阈值再由模型确认。确认重复后不新建记忆，而是给已有记忆增加一个证据引用（加强可信度）。
- 关键点：阈值需要用去重集画精确率-召回率曲线来选，不凭感觉定。误合并的代价比漏合并高（丢信息），应偏保守。

**3. 证据引用打通（当前上下文接口返回空数组）**

- 目标行为：上下文中每条记忆都能指到它的来源事件、角色与来源类型（用户直述、工具结果、模型推断）。
- 思路：项目已有证据表并在写入，只需让上下文构建器在选中版本后查询它。再根据来源类型给“可信度等级”，把原来统一的“未验证”细分。
- 关键点：这是基准导入时“记忆到来源会话”映射的前置任务，也为冲突处理提供“谁说的、什么时候说的”依据。

**4. 衰减与归档**

- 目标行为：长期不被检索到、重要性低的记忆逐步降权或归档，记忆库不无限膨胀，同时不掉质量。
- 思路：用“最近使用时间、重要性、年龄”组合打分；低分记忆走项目已有的归档状态（可恢复），不直接删除。
- 验证：在记忆库逐步增长的模拟中，对比“有衰减”和“无衰减”的库体积、延迟与 RT1。衰减参数用开发集调。

### 优化的依赖顺序

1. 先完成“基线 B0 + 评测框架”（第 11 节阶段 0 到 2）。
2. O1、O4、O5、O10 彼此互相独立，可并行。
3. O2 依赖 O1 的分阶段归因结果，以便确认向量召回确实是瓶颈。
4. O8 的证据引用打通先于冲突处理，冲突处理先于 O3 中“知识更新”题型的优化。
5. O3 在 O8 之后做第二轮，因为记忆库质量变了，检索的表现也会变。
6. O9 最后做，综合所有改动的最终端到端对比。

### 优化故事页的讲法

每个故事用同一个结构讲，三分钟讲完，不展开实现细节，除非被问：

1. **现象**：一句话说出问题和影响，带基线数字。例如“在 X 规模下搜索 p99 为 Y”。
2. **定位**：怎么找到原因的，用了哪个测量。不是“我觉得”，而是“测到”。
3. **假设与实验**：改了什么，一次只改一件事，对照是什么。
4. **结果**：前后数字、置信区间或波动范围、在哪个数据集上。
5. **代价**：这个优化牺牲了什么，必须如实写出。
6. **还能做什么**：下一步和边界，说明这个优化的天花板在哪。

“结果不好”也是合格的故事，前提是写清为什么，以及后来怎么调整。比如“重排提升了召回但 p99 超标，所以最终没有采用”，这比“全部变好了”更可信。

### 讲述原则

- 先结论后细节，每次回答不超过三句话，等对方追问再展开。
- 分清三类事情：“测过的”“推断的”“没做的”。不把后两类说成第一类。
- 不使用“生产环境”“真实用户”这类词来描述合成数据的结果。
- 不说“我们的系统一定优于 X”，只说“在这个评测下得到这样的结果”。
- 指标计算（Recall@k、MRR、p99）要有手算可验证的样例，报告里解释为什么 p99 比平均值重要。
- 每个阶段交接时附原理说明，由项目负责人核对后才进入下一阶段。

### 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 评测集质量不足 | 所有结论不可信 | 两个标注模型间一致性 κ ≥ 0.7；不一致条目由负责人仲裁；模型起草的题目必须抽检 |
| 裁判模型有偏差 | 问答类指标失真 | 人工抽检校准；不达标的指标改人工评；裁判与标注、抽取、答题模型不同厂商（见第 7 节） |
| 公开基准可能已被模型“见过” | 分数偏高 | 报告中写明这一局限；中文自建集的语料选用较新或重新改写的内容 |
| 英文基准与中文场景差异 | 把英文分数当成中文效果 | 中文结论只来自 PerLTQA 和自建中文集 |
| 合成压测向量不代表真实分布 | 近似索引的召回和延迟失真 | 首期全部使用真实向量；将来引入扰动向量时标注占比 |
| 压测环境有噪声 | 结果不可复现 | 环境指纹文档、预热、重复、报波动，发压端和被测服务分开 |
| 评测用量过大 | 评测耗时过长或被限流 | 先按第 7 节公式估算调用量再开跑；先抽样再全量；遇限流（429）退避重试，记录 token 用量 |
| Ark 限流或模型版本变化 | 结果不可比 | 记录模型版本和调用日期；缓存已计算的向量和裁判结果，固定在基线里 |
| 改动互相干扰 | 无法归因 | 一次只改一件事，独立分支，每次合并前跑回归测试，绝对正确性指标下降即阻断 |
| 语料协议不允许展示 | 材料不能公开 | 数据集清单记录协议；不清楚的只本地使用，材料里只写方法和指标 |
| 进度失控 | 越做越散 | 阶段闸门（第 11 节）；每个阶段只关注该阶段的验收标准 |
| 评测模型额度耗尽或模型下线 | 评测中断，模型组合反复更换，分数不可比 | 裁判按第 7 节“裁判选择与切换规则”处理；标注模型额度不足时可自动切换，切换后整批重标；开跑前记录调用量估算，额度用完由自动切换兜底 |

5. 每个阶段交接包包括：代码提交、报告、运行命令、环境指纹、遗留问题。只有项目负责人确认验收通过，才进入下一阶段。
6. 发现“绝对正确性指标”退化时，立即停止后续工作，先修复，不询问是否继续。

## 14. 开发过程记录规范

**每一次开发都要留下“别人能看懂、能复现”的记录，没有记录的任务不算完成。** 记录要说清楚怎么写的、用了什么模型、用了什么技术手段，读者是不了解项目的工程师，也包括日后复盘的人。

### 存放位置与流程

- 记录放在仓库 `docs/devlog/`，每个任务一个文件，文件名形如 `2026-10-20-任务编号-简短名称.md`，并维护 `docs/devlog/INDEX.md` 作为总索引。
- 记录和代码在同一个提交里，或紧跟在后面的提交里，并写明提交号。
- 报告里的每个数字，都要能链接到产生它的那条记录。
- 由开发 Agent 在完成任务时写，项目负责人审阅，复核方抽查。

### 每条记录必须包含的内容

| 字段 | 内容 |
| --- | --- |
| 任务与目标 | 对应本方案哪一节、哪个指标编号或优化故事编号，一句话说清要解决什么问题 |
| 设计思路 | 选了什么方案、考虑过哪些备选、为什么放弃 |
| 怎么写的 | 改了哪些模块和文件，核心做法用文字说清原理，关键参数的取值和理由；不贴大段代码 |
| 技术手段与依赖 | 使用的库及版本、数据库参数、索引类型及参数、压测或评测工具 |
| 写代码用的 AI | 哪个 AI 工具、哪个版本、交给它的任务说明存放在哪里；哪些部分由 AI 编写，哪些由人修改或审阅 |
| 运行时用到的模型 | 角色（抽取、向量、标注 A、标注 B、裁判、答题）、平台、模型名和版本、调用日期、关键参数（温度、维度等）、提示词版本号 |
| 数据 | 数据集名、版本或提交号、哈希、切分方式、是否合成 |
| 怎么跑 | 一条命令、环境指纹、随机种子 |
| 结果 | 前后对照的指标表、波动范围或置信区间、报告文件路径 |
| 问题与处理 | 遇到的坑、失败的尝试、怎么解决的 |
| 代价与风险 | 这个改动牺牲了什么、还有什么没做 |
| 费用与用量 | 调用次数、token 用量、折算费用 |
| 提交与评审 | 分支、提交号、项目负责人的审阅结论 |

### 模型调用台账

除了每条记录里的“运行时用到的模型”，还要有一张全局的模型调用台账，由调用封装自动记录，不要手填：

| 列 | 说明 |
| --- | --- |
| 时间 | 调用时间 |
| 任务编号 | 对应哪条开发记录 |
| 角色 | 抽取、向量、标注 A、标注 B、裁判、答题 |
| 平台与模型版本 | 火山 Ark 或腾讯云、模型名和版本标识 |
| 关键参数 | 温度、维度等 |
| 提示词版本 | 对应提示词文件的版本号 |
| 输入输出 token | 用量 |
| 折算费用 | 按单价参数折算，不写死价格 |
| 是否命中缓存 | 标明是否由缓存提供，避免重复计费被误算 |

台账里不记录记忆正文和答案正文，只记编号和用量，防止台账本身变成数据泄漏点。

### 提示词版本管理

- 所有提示词（抽取、标注、裁判、答题）都存成文件，带版本号和变更说明，不写死在代码里。
- 改提示词视同改代码：要写开发记录，并重跑受影响的评测。
- 裁判和标注的提示词一旦在基线中使用就冻结，要改必须重测基线。

### AI 辅助的诚实记录

项目代码由 AI 工具辅助完成，这本身不是问题，问题是说不清楚。记录里如实写明哪些由 AI 编写、哪些由项目负责人审阅或修改；目标、设计、验收标准由负责人定，关键机制要有原理说明。没有读懂的内容，不写成“我实现的”。

### 验收与阶段闸门

在第 11 节每个阶段的验收标准之外，增加三条：

1. 本阶段的所有任务都有开发记录，字段齐全。
2. 抽查两条记录，由不参与实现的一方按记录复现，不需要再问开发 Agent。
3. 记录里的数字和报告里的数字一致。

### 写作要求

- 先写结论，再写过程。
- 不写真实个人信息，也不贴记忆正文。
- 用中文，语句简短，原理优先。
- 每条记录写清“还有什么没做”，不要只写成功的部分。
