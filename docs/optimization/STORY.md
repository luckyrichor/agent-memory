# 优化故事

写给负责人本人，用来面试讲述。所有数字都能追到 `measurements/` 下的文件或提交号；追不到的，这里会直接说"没有"。

---

## 1. 这个项目是什么

一个跨会话的 Agent 记忆服务：Python 3.12 / FastAPI / PostgreSQL 16 + pgvector，多租户，行级安全（RLS）。

两条主链路：

- **写**：事件 → outbox → job → 抽取 worker → 候选记忆 → embedding job → 向量
- **读**：查询 →（词法 + 向量 + 结构化）三路候选 → RRF 融合 → context 打包

起点是一份来自 Agent 侧的重做报告：抽取候选永远不会变成 `active`，全链路检索恒为 0；1 QPS 起搜索接口大量超时（1 万规模 64% 错误，10 万规模 98%，p95≈30 s）。

我接手后先做的不是优化，是**把"到底慢在哪"量出来**。

## 2. 我先量了什么，发现了什么

| 我先量了 | 发现 |
|---|---|
| 单条检索的耗时构成 | 词法宽查询 1.9 s，其中绝大部分是**把整行正文连同向量一起搬出来**，而真正只用前 20 条 |
| 三路查询的执行计划 | 词法通道**没走索引**——`to_tsvector` 是每次现算的表达式，GIN 用不上；而且 RLS 下也用不上 |
| 抽取到可检索的延迟（稳态） | 7.3 s，其中大部分是 worker 在**空闲时睡觉**，醒了才发现有活 |
| 同一延迟（突发积压） | 42.4 s，因为 worker 每条任务之间都要睡一次 |
| 池耗尽时的行为 | 挂 30 s 然后 500，而不是快速失败 |
| 向量通道的形状 | 先 join 三张表再整体排序，等于把租户过滤和排序混在一次大扫描里 |

关键的判断：**慢的原因不在数据库参数，也不在 SQL 写得好不好，而在"搬了多少用不上的东西"和"等了多少本不必等的时间"**。

## 3. 每一项优化

下面每一条都给"问题 / 原因 / 做法 / 数字 / 还不能说的话"。**没起效的也写了**。

### B1 两段式检索 —— 没起效，但保留

- **问题**：三条查询各取最多 1000 行，每行都带完整正文，融合后只用前 20 条。
- **做法**：通道只返回 `memory_id / version_id / score`，融合排序后只对当前页取正文。
- **数字**（1 万行，2 核同机，pgvector 0.6.0，p50 中位，前后各 3 次）：词法窄 679.2 → 673.1 ms；词法宽 1862.0 → 1868.5 ms；词法+结构化 655.8 → 629.8 ms；向量+词法 775.0 → 719.3 ms。
- **结论**：**传输量降了，延迟没动**。范围互相重叠，不能声称变快。
- **为什么保留**：它是 B2 和 E1 的地基——正文和证据都只能按页取。留着并把"没效果"写进文档，比悄悄删掉再讲一个漂亮故事诚实。
- **不能说的话**：不能说"两段式提升了性能"。

### B2 词法通道换存储列 —— 最大的一次收益

- **问题**：`to_tsvector('english', content)` 是写入时就该算好的东西，却在每次查询时现算。
- **做法**：迁移 0010 增加 `lexical_en` / `lexical_zh` 两个**生成列**（中文用等价的分词函数），查询直接命中存储列。
- **数字**（同上环境，p50 中位）：词法窄 673.1 → 10.8 ms；词法宽 1868.5 → 68.7 ms；词法+结构化 629.8 → 24.3 ms。数据库侧 EXPLAIN：窄 626 → 13.1 ms，宽 1778 → 74.4 ms。
- **代价**：写入时多算一次、多存一列；迁移期间要回填。
- **不能说的话**：GIN 索引在这个负载下仍然用不上（RLS 过滤 + 表达式），所以"加索引"不是这里的功劳，换存储列才是。

### B3 向量索引：量完之后，决定**不加索引**

- **问题**：`memory_embeddings` 没有向量索引，检索是精确扫描 + 过滤。常规答案是"上 HNSW"。
- **我先量了三件事**（tx 服务器 Docker `pgvector/pgvector:pg16`，pgvector 0.8.6，客户端与库同机，8 千 / 2 万向量 × 候选上限 1000 / 100）：
  1. 候选上限取生产默认 1000 时，**规划器从不选 HNSW 索引**——8 千行、2 万行都一样。建了索引也不选。
  2. 真正起效的是**查询形状**：先在 `memory_embeddings` 上取最近邻（物化 CTE），再关联 `memories` 过滤状态。即使**没有索引**，8 千行 126.8 → 61.5 ms，2 万行 239.2 → 111.7 ms，约 2 倍；召回@20 全为 1.0。
  3. 只有把候选上限压到 100，索引才会被选中：原始两步 SQL 14.5–18.0 ms，但召回掉到 0.4983–0.7967。`ef_search=40` 且无迭代扫描时，**候选只剩 23 条**——这就是"过滤把近似扫描截断"的真实故障。
- **做法**：只上查询形状（`vector_search="nearest_first"`，默认开），**不加索引迁移**（`0014_vector_hnsw_index` 已删除）。索引写成运维可选步骤，前置条件是 pgvector ≥ 0.8 的 `hnsw.iterative_scan`。
- **不能说的话**：① 召回数字不是检索质量——夹具是聚类合成向量（50 个中心 + 噪声 0.3），不是语义向量。② 我只有 2 万，没有 10 万。③ 我不能说"HNSW 没用"，只能说"在当前查询形状 + 候选上限下规划器不选它"。

### B4 连接池耗尽 —— 快速失败

- **问题**：池耗尽时请求挂 30 s，然后一个没有语义的 500。
- **做法**：池参数可配，`pool_timeout` 默认 2 s，超时映射成 503 + `Retry-After`。
- **证据**：`tests/integration/test_pool_exhaustion.py`（并发把池占满，断言 503 与响应头）。
- **不能说的话**：**没有做压测**。这是行为正确性验证，不是性能验证。

### C1 worker 不再空转睡觉

- **问题**：worker 每条任务处理完都睡固定间隔，有积压时也在睡。
- **做法**：有活就继续领，只有真的空了才等。
- **数字**（突发积压，同一脚本同一数据，前后各 3 次）：`extraction_visible` p50 **42.396 s → 0.598 s**，整批清空 81.1 s → 1.3 s。

### C2 `LISTEN/NOTIFY` 触发式唤醒

- **问题**：C1 之后仍有轮询间隔的尾巴。
- **做法**：`jobs` / `outbox_messages` 插入时 `pg_notify`，worker 用独立连接 `LISTEN`；低频轮询保留作兜底。租约、围栏、`FOR UPDATE SKIP LOCKED` 都没动——通知只负责"叫醒"，能不能领仍由数据库状态决定，所以通知丢失或重复都不影响正确性。
- **数字**（稳态）：`extraction_visible` p50 **7.307 s → 0.041 s**，`vector_ready` 7.723 → 0.064 s。

### C3 单进程多并发消费

- **数字**：`--concurrency 1` vs `4`，突发积压下 `vector_ready` p50 6.88 s → 1.984 s，整批清空 13.6 s → 4.0 s。
- **不能说的话**：没有测更高并发，也没有测多 worker 抢同一租户时的租约竞争；数字只有 1 个规模。

### C4 任务优先级（交互写入 > 批量导入）

- **问题**：`jobs` 只有 `available_at / created_at` 排序，领取是纯 FIFO。批量导入一灌，用户的交互写入排在几千条后面。
- **做法**：`jobs.priority`（`BULK=0` / `INTERACTIVE=100`）+ `ix_jobs_claim_order`；领取按 `priority DESC`，同优先级内部仍是 FIFO，默认 0 与改动前等价。优先级要**跨两跳**传：outbox 消息带 priority → `extract_event` 继承 → 抽取事务里设 GUC `app.job_priority`，让触发器生成的 `embed_memory` 也继承。只改第一跳的话，交互事件仍会卡在别人的 embedding 任务后面。
- **数字**（1500 条 bulk 积压 + 5 条交互事件，每配置 3 次）：交互事件 ingest → active 的 p50 = 40.952 / 24.018 / 29.748 s（中位 29.7 s）对 0.445 / 0.076 / 0.223 s（中位 0.22 s）。**两组范围互不重叠**。
- **代价**：bulk 的 p50 中位 21.9 → 25.3 s，这是 5 条任务插队应付的账。
- **不能说的话**：① 只有 1 个 worker、1 个客户端，不是吞吐结论。② 没有测优先级造成的**饥饿**。③ outbox → job 这一跳仍不分级。

### C5 向量复用

- 同租户、同模型、**完全相同**正文的向量只算一次，键是 `(租户, 模型, 正文 SHA-256)`，不跨租户。
- **证据只有单测/集成测试**（计数提供器断言调用次数），**没有规模化测量**。

### D 系列：错误语义、日志、删除清理

- D1 查询文本不进日志/span：写成守卫测试（覆盖搜索、事件、worker），当前代码未发现泄漏点。
- D2 磁盘满 / 数据库不可用映射成 503 与稳定错误码：**只有单测模拟 SQLSTATE**，没有真的写满磁盘。
- D3 逻辑删除后的正文清理：手动命令 + 集成测试（清理后正文与向量都读不到），没有自动调度。

### E1 证据引用 —— 有代价，值得

- **做法**：检索结果每条带至多 5 条证据引用、context 每条带至多 3 条 `{event_id, role}`。**只有事件 id 和调用方自己的坐标**（session / sequence / 时间），没有事件正文。证据只对当前页用一条窗口函数查询取回。
- **数字**（1 万行，无向量，p50 中位，各 3 次）：词法窄 10.5 → 13.5 ms；词法宽 65.9 → 67.6 ms；词法+结构化 25.4 → 27.0 ms。前后范围不重叠，即每条多 1.6–3 ms。
- **不能说的话**：① 只有抽取路径产生证据，显式写入的记忆没有来源。② 引用只是指针，**不等于"已验证"**。③ 对最快的查询，3 ms 的相对比例不小。

### E2 精确重复去重

- 同租户同作用域、规范化后完全相同的候选，不新建记忆，只追加一条证据。
- **不能说的话**：只覆盖抽取路径；并发竞态没处理（见 PLAN 交接日志）。

### E3 上下文打分 —— 机制对了，权重没调

- **做法**：总分 = 相关度（本页归一）+ 新旧（0.5^(年龄/半衰期)，按记忆类型 14/180/365 天）+ 可信度（`authority_level` / 5）；装入时按 `分数 ÷ 占用` 贪心，相关度低于门槛的不装。元数据走页级一次查询。
- **为什么按"分数÷占用"**：预算是稀缺资源，"短且几乎同样相关"比"长且略好一点"更值。
- **验证**：单测 16 个（三因子各自能改变顺序、确定性、缺时间戳按中性 0.5）、集成 3 个（真库元数据、跨租户、同分时权威高的在前）。
- **不能说的话**：权重 1.0 / 0.3 / 0.3 和半衰期都是**起点值**，必须在开发集上选。我没有开发集，也没有真实向量，所以**没有任何质量结论**。

### E4 冲突标注 —— 只做词面规则

- **做法**：同一主体、同一记忆类型、词面重叠（Jaccard ≥ 0.6）但正文不同的两条，互相标 `{"memory_id", "reason": "similar_text"}`。
- **为什么不用 `contradicts` 证据角色**：写路径只产生 `triggered_by` 和 `supports`，没有任何生产者写 `contradicts`。按那个角色标就是一个永不触发的功能。
- **不能说的话**：① 短句失效——"我住北京"和"我搬到上海"几乎没有共同 bigram，标不出来（这条的测试就是断言它标不出来）。② 语义冲突需要模型，超出范围。③ 措辞相近但相容的两条会被误标；这个字段只是提示，不修改存储。

## 5. 可能被追问的十个问题

1. **"为什么不上 HNSW 索引？这不是标准做法吗？"**
   因为量了之后规划器根本不选它。候选上限 1000 时，8 千行和 2 万行都不选——精确扫描在那个宽度更便宜。硬上索引等于给运维一个不起作用的对象。真正值钱的是查询形状，它不需要索引就有 2 倍。

2. **"你的召回率数字能说明检索质量吗？"**
   不能。那是聚类合成的 1024 维向量，不是语义 embedding。它只能说明"形状和索引的行为"，不能说明"找得准不准"。质量要等真实模型重跑开发集。

3. **"相关度为什么按本页最高分归一？"**
   因为 RRF 分数没有绝对量纲，取决于有几个通道命中。任何"绝对阈值"看上去有道理，其实只是把页大小写死。

4. **"E3 的权重 1.0 / 0.3 / 0.3 是怎么定的？"**
   是起点值，我明确没有调。调它需要开发集和真实向量，我两样都没有。我验证的是机制和确定性。

5. **"你说标了冲突，你凭什么判断两条记忆矛盾？"**
   我没有判断矛盾。我标的是 `similar_text`——同一主体、同一类型、词面高度重叠但正文不同。这是"被改了口"的形状，也是"无害改写"的形状，所以字段名和文档都写成提示而不是结论。

6. **"优先级会不会让批量导入饿死？"**
   会，只要交互写入持续不断。这是已知代价，我没有测饥饿，也没有做老化（aging）。现在的实现是"两档 + 同档 FIFO"，最小的可用版本。

7. **"这些延迟数字能代表线上吗？"**
   不能。客户端、服务、数据库在同一台机器上，没有网络，没有真实并发。它能说明**相对**效果（A 改完比 B 快多少），不能当正式压测。

8. **"B1 没效果，为什么还留着？"**
   因为它把"通道只返回 id"这件事固定下来了，B2 和 E1 都建在上面。一个没效果的改动，我也照实写进文档，不删掉换个说法。

9. **"证据引用会不会拖慢检索？"**
   会，每条多 1.6–3 ms。对快查询（10.5 ms）相对比例不小，对宽查询几乎看不出来。所以它是一条明确的代价，不是免费的。

10. **"你怎么保证这些改动没破坏正确性？"**
   四道门每次提交前全量跑：pytest（571 passed）、ruff、mypy strict（108 文件）、foundation_runner（8/8，0 租户泄漏，0 删除后命中）。关键的安全不变量有独立测试：跨租户读数、RLS 下应用角色、删除后正文不可读。E1 和 E3 的关键行为还做了变异验证（去掉排序/去掉透传，对应测试各自失败）。

## 6. 如果换成真实流量，结论可能怎么变

- **词法那 60 倍**大概率会缩水：真实正文更长、词更分散，存储列的优势仍在，但基数不同。
- **向量那 2 倍**可能变好也可能变差：真实 embedding 的分布不同于合成聚类，候选上限 1000 下索引是否会被选中，需要在真实数据上重看执行计划。
- **C4 的 130 倍**是一个极端场景（1500 条积压）的上界，日常负载下这个差距会小很多，但**方向不会变**：FIFO 下交互写入的等待时间正比于积压深度，优先级把它变成常数。
- **E3/E4 完全没有线上证据**，它们只是"机制可用"，不是"效果更好"。

## 7. 诚实边界（一句话版）

没有模型密钥，所以**所有质量结论都不存在**：本仓库里的数字全是延迟、吞吐、调用次数、行为正确性，以及"这段代码确实按设计跑了"。真实的质量提升需要你用同一份 B0 配置在本分支上重跑开发集，那是第 9 节第 3 条留给你的活。
